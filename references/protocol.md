# 接力协议规范

## 设计目标

上下文传递的成本来自"重述"。完整对话历史动辄几万 token，而真正让新智能体能干活的信息只有一小撮。本协议把这些必要信息压缩进固定字段，目标是让交接材料控制在 200-400 token，同时保证接手方不会重复劳动、不会推翻已有结论、不会踩同一个坑。

## 状态文件字段定义（HANDOFF.md）

文件名默认 `HANDOFF.md`，放在任务工作区根目录，可由用户改路径。各字段作用如下：

| 字段 | 必填 | 作用 | 填写要点 |
|------|------|------|----------|
| `last_updated` | 是 | 判断信息新鲜度 | ISO 格式时间 |
| `current_owner` | 是 | 谁在写 | 智能体/平台名 |
| `task` | 是 | 任务名 | 一句话 |
| `goal` | 是 | 最终目标与验收标准 | 可量化，**注明测量口径**（如"5 折 CV 均值"而非"单次切分"） |
| `stack` | 是 | 技术栈与环境 | 语言/框架/版本/**已装依赖**/离线或联网；`next_action` 用到的工具必须在此出现 |
| `constraints` | 否 | 硬约束与用户偏好 | 格式、语言、UI、禁用项 |
| `decisions` | 否 | 已定决策 | 每条 `决策 → 理由`，一条不可删 |
| `progress.done` | 是 | 已完成事项 | 带结论或产物指针 |
| `progress.in_progress` | 否 | 进行中及卡点 | 写清卡在哪 |
| `progress.todo` | 是 | 待办 | 按优先级排序 |
| `artifacts` | 是 | 产物索引 | `路径 → 一句话说明`，只写指针 |
| `gotchas` | 否 | 已知坑 | `失败路径 → 原因`，全量记录不可删 |
| `next_action` | 是 | 下一步第一动作 | 具体到可执行，**工具须已在 stack 中** |
| `handoff_log` | 否 | 交接记录 | 每次交接追加一行 |
| `接手须知` | 是 | 给下家的操作规则 | 改 owner、按 goal 口径验收、三"严禁" |

### 四条铁律

1. **指针化**：产物索引用路径和一句话说明，不贴代码、不贴文档正文。让接手方用工具去读文件。
2. **决策带理由、不可删**：写"用了 X → 因为 Y"。下家遇到同样岔路时才不会重新论证、不会推翻。
3. **坑全量搬运、不可删**：已知坑是最容易在压缩时丢掉、代价却最大的信息。交接时逐条复制，一条都不能少。
4. **依赖一致性**：`next_action` 提到的工具/依赖必须已在 `stack` 中列出。测试发现这是高频陷阱——"建议用 optuna"但目标机器离线且未装 optuna，接手方第一步就卡死。要么在 stack 补上，要么改用已有工具。

## 接力卡片规范

卡片是纯文本，由当前智能体在额度将尽时输出，用户复制粘贴给下一个智能体作为第一条消息。卡片采用**固定 8 字段编号结构**（①-⑧），防止自由发挥导致关键信息（尤其约束和坑）被省略。硬性要求：

- 200-400 token，八段齐全：目标(含量化口径) / 技术栈环境 / 已完成 / 决策(不可删) / 产物指针 / 已知坑(不可删) / 待办 / 你现在要做的。
- 末尾附 `last_updated` 与原 owner，便于判断新鲜度与责任归属。
- 不含寒暄、不含过程性叙述。
- 输出前按模板自检清单逐项核对。

## 接力时机判断

- 用户明确说"额度快没了 / 要换平台 / 接力"时立即触发操作 C。
- 长任务预估剩余步数接近平台免费额度时，主动提醒用户："额度可能即将耗尽，建议现在交接"。
- 宁可早交接：状态文件是增量维护的，早交不丢信息，晚交可能来不及落盘。
