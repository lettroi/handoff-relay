# Handoff Relay — 跨智能体长任务接力协议

> 免费额度用完就换 AI 继续干活，但不想每次都把整个对话历史重贴一遍。
>
> 把上下文从对话里剥离出来，压成一张 200–400 token 的接力卡片。换平台不换脑子。

## 有什么用

主流 AI 智能体（WorkBuddy、豆包、千问、ChatGPT……）大多按天给免费额度，一个稍长的任务很容易做到一半就见底。此时的常规做法是：把之前的对话复制给下一个平台的智能体，让它接着做。

问题在于，对话历史动辄几万 token，其中 95% 是工具调用、来回澄清、失败尝试——真正让新智能体能接着干活的信息只有一小撮。重贴整段历史既烧额度，又容易让新智能体抓不住重点，甚至重复劳动、推翻已经定好的方案。

**Handoff Relay 提供一套固定格式的状态文件 + 接力卡片**，让每次切换只传递"必要的一小撮"：

- 目标与**验收口径**（写清是 5 折 CV 均值还是单次切分）
- 技术栈与**已装依赖**（防止"建议用 optuna"但目标机器离线没装）
- 已完成事项（带产物指针，不重做）
- 已定决策**及其理由**（不被推翻）
- 产物路径索引（只给指针，让新智能体自己去读文件）
- 已知坑（逐条保留，不重复踩）
- 下一步第一动作（接手就能干）

## 为什么需要

一次冷启动测试说明了问题。我们把一份"看起来很完整"的交接材料交给一个全新智能体（只给它材料、不给对话历史），它准确指出了这些缺陷：

- 下一步建议用 `optuna`，但技术栈清单里没有它，目标机器还离线 —— **第一步就可能卡死**
- 验收只写"AUC ≥ 0.85"，没说是交叉验证还是单次切分 —— **无法判断何时算达标**
- 卡片在压缩时漏掉了"不存特征交叉"的决策和"目标机器离线"的约束 —— **最容易丢的恰恰是代价最大的信息**

这揭示了一个反直觉的事实：**上下文传递的瓶颈不是"信息量不够"，而是"关键信息在压缩中被无声地丢掉"**。所以本协议不是简单的摘要模板，而是把那些最容易被丢、代价最大的字段做成强制项：

| 机制 | 解决的问题 |
|------|-----------|
| 固定 8 段编号结构 ①–⑧ | 防止自由发挥导致约束/坑被省略 |
| `stack` 技术栈必填 + 依赖一致性检查 | 防止下一步动作依赖不可用工具 |
| 决策/已知坑标注"不可删" | 防止压缩时丢掉最难获取的信息 |
| 验收口径注明测量方式 | 防止"达标"标准各说各话 |
| 接手须知三"严禁" | 防止重做、推翻、重复踩坑 |
| 指针化（只存路径不存内容） | 把上下文成本从几万 token 压到几百 |

改进后重跑同一测试，接手方确认：工具可用性 ✓ 无问题、验收口径 ✓ 明确。

## 它怎么工作

三个动作，对应任务的三个阶段：

```
开工  →  过程中  →  额度将尽
 │         │           │
读卡片    增量维护    写状态文件 + 输出接力卡片
复述理解  只写指针    复制给下一个平台
更新owner 决策带理由  下家读卡片续作
```

- **开工恢复**：新智能体读卡片/状态文件，复述理解，更新 owner，然后续作。严禁重做已完成、推翻决策、踩已知坑。
- **增量维护**：每完成一个阶段性成果就更新状态文件，产物落成文件、索引只写指针，不等到交接时回忆。
- **生成接力卡片**：额度将尽时先落盘状态文件，再输出固定格式的 200–400 token 卡片，附自检清单防漏。

## 怎么用

### 在 WorkBuddy 中

本项目本身是一个 WorkBuddy skill（`SKILL.md`）。安装为本用户 skill 后，直接说"接力 / 交接 / 额度快没了 / 继续上次任务"即可触发。它会自动读写 `HANDOFF.md` 并按模板生成卡片。

### 在其他平台（豆包、千问、ChatGPT……）

这些平台没有 skill 机制，靠系统提示词驱动：

1. 打开 `assets/universal-prompt.md`，把虚线之间的内容复制到目标平台的"智能体设定 / 系统提示词 / 自定义指令"里。存成一个叫"接力员"的智能体最好——以后只换平台、不换提示词。
2. 从 `assets/PROJECT.template.md` 复制一份状态文件，命名为 `HANDOFF.md`，放到任务目录。
3. 任务过程中按模板增量填写（WorkBuddy 会自动做；其他平台可由智能体在对话里维护【工作记录】区块）。
4. 额度将尽时，让当前智能体按 `assets/HANDOFF-CARD.template.md` 输出接力卡片。
5. 复制卡片（必要时连同状态文件内容）作为第一条消息，发给下一个平台的"接力员"。

### 接力载体

| 载体 | 适用 | 做法 |
|------|------|------|
| 共享状态文件 | 各平台能访问同一路径（同一台机器、共享云盘同步目录） | 开工读、过程写、交接更新 |
| 纯文本卡片 | 任意平台，无法共享文件 | 复制卡片 + 状态内容粘贴给下家 |

协议格式一致，因此即使只能纯文本接力，上下文也不会走样。

## 设计原则小结

1. **指针化**：索引只写 `路径 → 说明`，内容留在文件里。
2. **决策带理由、不可删**：防止下家重新论证后推翻。
3. **坑全量搬运、不可删**：最容易丢、代价最大的信息。
4. **依赖一致性**：下一步用到的工具必须已在技术栈中出现且可用。

这四条来自真实的冷启动测试，不是拍脑袋的最佳实践。
